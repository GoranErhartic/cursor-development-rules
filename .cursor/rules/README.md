# Unified Cursor Rules

This folder contains a unified, language-agnostic rule system for Cursor AI agents that supports multiple programming languages while maintaining shared methodologies.

## Rule Activation Model

Cursor rules use three activation mechanisms. Understanding these is critical for efficient agent context usage.

### 1. Always Applied (`alwaysApply: true`)
Loaded into every agent interaction. Use sparingly — each token here costs on every request.

| File | Purpose | ~Size |
|------|---------|-------|
| `agent-behavior.mdc` | Persona, Never Assume, Rule Flagging; links to workflow/TDD/docs | ~45 lines |
| `project-context.mdc` | Project-specific routing: active stacks, directory→router mapping, key deps; generated by running project onboarding | ~30–40 lines |

**Note:** `project-context.mdc` is generated (or refreshed) by running the procedure in `development/project-onboarding.mdc`. If missing or placeholder-only, the agent should suggest onboarding. `retrospective.mdc` is agent-requestable. Use `rule-index.mdc` to discover all stack routers.

### 2. Glob-Activated (`globs: [...]`) — Routers Only
**Only the stack router** for each language is glob-activated. When you open a file in that stack (e.g. a `.tsx` file in a React project), only the router loads (e.g. `react-frontend.mdc`). The router lists all rule files by task type; the agent **loads specific rules on demand** for the current sub-task.

**Why:** Previously, broad globs caused 10+ rules to load at once (e.g. every React rule on any `.tsx` file), consuming 50k+ tokens. Now, opening a file loads only the router (~1k tokens); the agent reads the router and requests the 2–3 rules relevant to the current work.

**Auto-loaded files:** 2 always-applied + up to 5 glob-activated routers = 2–7 files in any session (only one router loads per stack).

- **Always-applied (2):** `agent-behavior.mdc`, `project-context.mdc`
- **Glob-activated routers (5):** `languages/aws-lambda/nodejs-lambda.mdc`, `languages/nodejs/nodejs-base.mdc`, `languages/java/java-spring.mdc`, `languages/csharp/csharp-dotnet.mdc`, `languages/react/react-frontend.mdc`

### 3. Agent-Requestable (no `alwaysApply`, no `globs`)
All other rules are agent-requestable: the agent sees the `description` and requests the file when needed. This includes **all language-specific rules** (handlers, SQS, DynamoDB, forms, etc.), **pattern rules**, and **development workflow rules**. Descriptions must be keyword-rich for discoverability.

## Supported Languages

### AWS Lambda / CDK / TypeScript
- **Router (glob):** `nodejs-lambda.mdc` — loads when Lambda/CDK paths are open
- **All other Lambda rules:** Agent-requestable (handlers, SQS, SNS, DynamoDB, testing, etc.); agent loads 2–3 per sub-task via router

### Node.js / TypeScript (Base)
- **Router (glob):** `nodejs-base.mdc` — loads when `.ts` (excluding Lambda/React/CDK) or package.json is open
- **All other Node.js rules:** Agent-requestable; load via router for current task

### C# / .NET
- **Router (glob):** `csharp-dotnet.mdc`
- **All other C# rules:** Agent-requestable

### Java / Spring Boot
- **Router (glob):** `java-spring.mdc`
- **All other Java rules:** Agent-requestable

### React / TypeScript
- **Router (glob):** `react-frontend.mdc`
- **All other React rules:** Agent-requestable

## Access Pattern Strategy (Router + On-Demand)

1. **Always in context:** `agent-behavior.mdc` (persona, never assume, rule flagging) and `project-context.mdc` (which stacks apply, directory→router mapping). If `project-context.mdc` is missing or placeholder-only, suggest running project onboarding.
2. **When working in a stack:** The **router** for that stack loads (e.g. opening a `.tsx` file loads `react-frontend.mdc` only). Use `project-context.mdc` to know which router(s) apply when no matching file is open.
3. **Agent reads router** and requests the 2–3 rule files relevant to the current sub-task (e.g. forms, validation, accessibility).
4. **Pattern and development rules** are always agent-requestable; agent requests them when the task requires (e.g. TDD, clean-code, api-design, project onboarding).

**Token budget target:** Keep rules in context per sub-task under ~15k–20k tokens (router ~1k + 2–4 on-demand rules ~4–8k + always-applied ~1k), leaving most of the context window for code, tool output, and conversation.

## Adding a New Language

See `languages/_template/README.md` for detailed instructions.

Quick steps:
1. Create `languages/your-language/` folder
2. Create `.mdc` files following the template structure
3. Set appropriate `globs` for file matching (avoid overlap with existing languages)
4. Reference universal patterns from `../../patterns/`
5. Focus on language-specific implementations

## Rule File Format

Each `.mdc` file uses frontmatter and Markdown:

```markdown
---
description: "Keyword-rich description for agent discoverability"
globs: ["**/specific/paths/**/*.ext"]   # Optional: when to auto-activate
alwaysApply: true                        # Optional: always active (use sparingly)
tags: ["testing", "security"]            # Optional taxonomy tags
relatedRules: ["other-rule.mdc"]         # Optional cross-links
---

# Title

## Content
Rule content in Markdown...

**See also:** Links to related rules
```

### Description Best Practices
- Include **specific keywords** the agent might search for
- Name **specific tools/libraries** covered (e.g., "Middy v7", "Powertools Logger")
- Mention **specific patterns** (e.g., "partial batch failures", "batchItemFailures")
- Keep under 200 characters for readability

### Glob Best Practices
- Use **specific directory patterns** over generic wildcards
- Avoid `**/*.ts` in language-specific rules (too broad)
- Prefer `**/functions/**/*.ts` over `**/src/**/*.ts`
- Test that globs don't overlap with other language rules

## Contributing

When adding new rules:
1. Universal concepts → `patterns/`
2. Language-specific → `languages/{lang}/`
3. Always-active rules → root level with `alwaysApply: true` (rare, keep small)
4. Development workflow → `development/` (rare)

### Context Budget Guidelines
- **Always-applied:** Two files only (`agent-behavior.mdc`, `project-context.mdc`), combined target &lt; 100 lines so rule discovery works without open files
- **Glob-activated (routers):** One router per stack, ~60–80 lines each; only these use globs
- **Agent-requestable:** Target &lt; 200 lines per file for slimmer context when loaded; conventions and key patterns over full copy-paste examples
- **Per sub-task:** Aim for &lt; 15k–20k tokens from rules (router + 2–4 on-demand rules)
- **Descriptions:** Rich enough for the agent to decide without reading the file
- **Cross-references:** Include "See also" links so the agent can load related rules when needed
